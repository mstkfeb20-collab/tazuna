# 指標

二つに分ける。混ぜると、案件の出来と型の出来の区別がつかなくなる。

- **案件の品質指標**: この案件の成果物の品質。工程の出口で案件リーダーが判定し、従来の品質報告に載せる。
- **月次の指標（型の指標）**: ハーネス（tazuna）が効いているか。標準化チームに共有する。案件の優劣を付けるためではない。

## 案件の品質指標

考え方: AI でコードを書く工程は、人が成果物を検査する代わりに、**仕組み（設計とゲート）を管理する**。品質を作り込むのは設計（人）で、実装と単体テストはゲート（機械）が確かめ、確かめきれたかは結合テストへの流出で検証する。

### 設計（ID 設計書）

| | 内容 |
| --- | --- |
| 指標 | **人のレビュー指摘密度**（指摘件数 ÷ 規模）。従来の設計レビューと同じ |
| 規模（分母） | 決定の行数（`- [n] 本文` の行。廃止の行を除く。`id_design.py progress` の「書いた（n行）」）。見出し・空行・図の行は数えない。Markdown には枚数がないので、行数をそのまま分母にする。基準値は、従来の枚数あたりの基準値を「1枚あたりの決定の行数」で割って、行数あたりに換算する（例: 1000枚で 0.010〜0.016 件/枚、1枚あたり 20 行なら 0.0005〜0.0008 件/行）。1枚あたりの行数は、パイロットで従来の設計書と同じ範囲を書いた実物から一度だけ決める |
| 集計の単位 | PR ごとに記録し、判定は機能群か工程全体でまとめて行う（件数が少ないと偶然の揺れが大きい）。PR ごとの値は、異常を見つける目印にだけ使う（大きい PR なのに指摘 0 件など） |
| 数えないもの | スキル `base-design-review` の点検の結果。点検はレビューではなく、人のレビューを始める条件（Lint COMMON-011）。件数は品質の指標にしない |
| 基準値 | 過去の基準値は「人だけでレビューした」前提の値。点検で形式・噛み合いの問題が先につぶれるので、人の指摘は下がるはず。**パイロットで新しい基準値を作る**。それまでは推移で見る |

**指摘の記録**: レビューのコメントの先頭に分類を書く。集計はコメントの先頭で数える。

| 分類 | 当てはまるもの | 品質の判定 |
| --- | --- | --- |
| `[誤り]` | 業務として、または書類どうしで正しくない | 入れる |
| `[欠落]` | 書くべきことが書かれていない | 入れる |
| `[表現]` | 意味は合っているが、読み違える書き方 | 入れる |
| `[課題]` | 業務で決めることが出てきた（設計者のミスではない）。issue にする | **入れない**（件数は別に報告する） |

- 課題が決まって設計書を直す PR も設計レビューとして扱い、そこで出た指摘は数える。決まったこと自体は数えない。
- 再レビュー（直したことの確認）は数えない。再レビューで**新しく出た**指摘は数える。

**見つかった場所**: 設計の PR で見つかったものと、**転記の PR** で見つかったもの（機能の横断面で初めて見えた設計の誤り・欠落）を分けて記録する。転記の PR は設計工程の最後の検査として扱い、指摘密度には合算する。転記の PR での指摘が多ければ、書類ごとのレビューで書類をまたぐ観点が抜けている。転記ツールの誤りは案件の品質に入れず、月次の rule-log へ。

**出口基準**: Lint が通る（COMMON-007・011）、止める種別の点検結果が残っていない（または理由付きで残す）、質問がすべて issue になっている、業務の担当者が承認している。

### 実装と単体テスト（AI）

人はコードをレビューしない。**ゲート（`mvn -B verify` と CI）を通ればマージしてよい**。そのぶん、ゲートの強さを数字で示す。

| 指標 | 見るもの | 取り方 |
| --- | --- | --- |
| テスト仕様の消化率 | 設計で決めたテスト観点が、すべてテストになったか（従来の試験密度の代わり。AI はテストの件数をいくらでも増やせるので、件数では見ない） | PR レポート（行IDの @Tag と「未対応」） |
| 分岐カバレッジ | テストが通っていない分岐がないか | JaCoCo（PR レポート） |
| ミューテーションスコア | テストが本当にバグを検出できるか（わざと壊したコードを検出した割合） | PIT（PR レポート） |
| セキュリティの指摘 | セキュリティの静的解析で見つかったもの（0 件でマージ） | SpotBugs ＋ FindSecBugs（PR レポート） |

- **基準値は品質計画で決める**: `pom.xml` の `tazuna.coverage.branch.min`（分岐カバレッジ）・`tazuna.mutation.min`（ミューテーションスコア）・`tazuna.mutation.targets`（対象の層）。エージェントは変えない。
- **単体のバグ密度は取らない**。エージェントはテストが通るまで自分で直してから PR を出すので、構造的に 0 件になり、指標として成り立たない。
- **実装の品質は、結合テストで見つかった実装起因の不具合で確かめる**。「ゲートを通ればOK」は宣言ではなく、この数字で確かめる仮説。多ければ、どのゲートで止められたはずかを rule-log に記録し、ゲートを強くする。
- 依存ライブラリの脆弱性は、`mvn verify` では見ない（脆弱性データベースの取得が社内プロキシで重い）。GitHub は Dependabot、GitLab は Dependency Scanning を有効にする。
- PR レポートの「設計由来のテストの書き換え」は、設計を変えずに、テスト仕様の行から作ったテストを書き換えた PR。期待値を実装に合わせていないかを確かめる。

**出口基準（単体工程の完了）**: 全要件が実装されている。未対応の行（未決・結合テストへ引き渡し）の一覧を試験チームに渡せる（スキル `base-navigator`）。

### 運用の注意

- `ID設計.xlsx`（機能一覧）は git でマージできない。課題の決定で機能一覧が変わる PR は、同時に複数を出さず、1本ずつ順に通す。

## 月次の指標（型の指標）

月次の見直しで案件リーダーが更新し、標準化チームに共有する。

| 指標 | 見るもの | 期待する動き |
| --- | --- | --- |
| rule-log の件数（防ぐ層ごと） | 仕組み化が進んでいるか | 「文章」の割合が下がる |
| 追加した Lint ルール数 | ミスがルールに変わっているか | 初期に増え、やがて落ち着く |
| PR数とリバート率 | エージェントの成果を信頼できるか | PR数が増えてもリバート率が上がらない |
| 同じレビュー指摘の再発数 | 改善が効いているか | 減る |

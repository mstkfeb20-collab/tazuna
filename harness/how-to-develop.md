# 開発の回し方（人とエージェントの分担）

tazuna で ID 設計から単体テストまでを進めるときの、**誰が・どのエージェントで・何をするか**。迷ったら、Copilot のチャットで「次は何をすればいい？」と聞く（案内役 `base-navigator`）。品質の考え方は [quality.md](quality.md)、設計書の書き方は [design-and-transcription.md](design-and-transcription.md)。

## 考え方

- **業務の決定は人、展開と実装は AI。** AI が仮に置いた業務の判断は「（案）」になり、人が確かめるまで決定にならない。
- **書く・点検する・作るを別にする。** 設計を書くエージェント、点検するエージェント、実装するエージェントを分け、自分で自分を採点しない。
- **人のレビューは業務に集中する。** 形式・噛み合いは点検と Lint、コードはゲート（テストの強さ・セキュリティ）が確かめる。

## エージェントの使い分け

| エージェント | 何をするか | 何をしないか | どこで使う |
| --- | --- | --- | --- |
| **設計の相棒** `design-partner` | 上流の入力（`docs/upstream/`）と業務の決定から、設計書のドラフトを一気に書く。業務の判断は「（案）」で置き、人と詰める。既存の決まりとの食い違いを探す | 業務を決める。実装・転記・点検 | VS Code のチャット（相談しながら）／GitHub で issue に割り当て（決定済みの issue） |
| **点検役** `design-check` | 設計書だけを読み、書類どうしの食い違い・未定義・抜けを指摘して記録する。質問を issue の下書きにする | 設計書を直す。業務として正しいかの判定 | **設計の会話とは別のセッション**（下の「点検役の動かし方」） |
| **実装**（素のエージェント。`AGENTS.md`） | 転記先（要件・テスト仕様・作業一覧）と DDL だけを根拠に、テストと実装を書き、ゲートを通して PR を出す | 設計書から決定を読み取る。未決・（案）の実装 | GitHub で issue に割り当て／VS Code |
| **案内役**（スキル `base-navigator`） | リポジトリと PR・issue の状態を読み、誰が次に何をするかを示す | — | どのチャットでも「次は何をすればいい？」 |

## 流れ

| # | 段階 | 人 | エージェント | 次へ進む条件 |
| --- | --- | --- | --- | --- |
| 1 | 上流をそろえる | 社員: 要求・外部設計・業務の説明を `docs/upstream/` に置く。決めたことは「業務の決定」issue に書く | — | 対象の機能の上流がそろう |
| 2 | ドラフトを書く | 社員: 対象と上流を伝える | 設計の相棒: 対象の書類を一気に書き、ドラフトの PR を出す。（案）を「レビュアーに判断してほしいこと」に並べる | ドラフトの PR が出る |
| 3 | （案）を確かめる | 社員: PR のコメントで `回答: 1 それでよい`・`回答: 2 21日前は0%`・`保留: 3` と答える（GitHub の Copilot の PR では頭に `@copilot`） | 設計の相棒: 答えどおりに直して（案）を外す。保留は issue の下書きにする | 業務の見出しに（案）がない |
| 4 | 点検する | 社員: 質問を issue にし、記録の「扱い」に番号を書く。止める種別は直すか「残す: 理由」 | 点検役（別のセッション）: 記録を付ける | 止める種別・未 issue の質問がない |
| 5 | 業務レビュー・マージ | 社員: ドラフトを外し、業務として正しいかをレビューしてマージ（GitLab は外したら Run pipeline） | — | CI（COMMON-011）が通る |
| 6 | 転記 | 社員: CI が出した転記の PR を、機能の横断面として確かめてマージ（出ていなければ手元で `transcribe.py`） | — | 転記の PR がマージされる |
| 7 | 実装 | 社員: 要件の issue を作って割り当てる。PR の質問に `回答: n` で答える | 実装: テストと実装、ゲート（カバレッジ・ミューテーション・セキュリティ）を通して PR | CI が通れば人はコードを読まずにマージ |
| 8 | 引き渡し | 社員: 未対応の行（未決・結合テストへ引き渡し）の一覧を試験チームへ | 案内役が一覧を出す | — |
| 9 | 不具合 | 試験チーム: 「不具合」issue で戻す。社員: 原因区分を決める | 原因が設計なら 1〜3 へ（業務の決定 → 設計の相棒）、実装なら 7 へ | — |

決まっていないことは、設計を止める理由にしない。質問を issue にすれば先へ進め、決まったらその issue から設計を直す（`Fixes #番号`）。

## 点検役の動かし方

書いた人の会話を引き継がないことが大事。

- **VS Code など手元**: 設計の PR のブランチで新しいチャットを開き、`design-check` を選ぶ。
- **GitHub**: 設計の PR に `@copilot` で頼まない（その PR の経緯を引き継ぐ）。エージェントの画面か issue から、エージェントに `design-check`、ベースブランチに設計の PR のブランチを選んで新しく頼む。出てきた小さな PR を、設計の PR のブランチにマージする。

## はまりやすいところ

| こと | なぜ | どうする |
| --- | --- | --- |
| Copilot のセッションが古いことを言う | セッションは、起動したときのリポジトリの写しで動く。main が進んでも中は変わらない | 状況が変わったら新しいセッションを立てるか、「main を取り込んでから」と頼む |
| Copilot の PR に答えたのに動かない | GitHub の Copilot は、メンションされないと動かない | コメントの頭に `@copilot` を付ける（案内役は付いていても答えとして数える） |
| Copilot の PR の CI が止まっている | Copilot の push ごとに、ワークフローの承認が要る | PR の「Approve and run workflows」を押す |
| `ID設計.xlsx` がぶつかる | Excel は git でマージできない | 書類やテーブルを足す PR（相棒の `list`・`scaffold` を含む）は、同時に1本だけにする。ぶつかったら後の方を作り直す |
| 型（tazuna）を直したのに案件に効かない | 案件はタグで型を取り込む | tazuna でタグを打ち、案件で `scripts/tazuna-update.sh <タグ>` の PR を出してマージする |
| 自動で出た転記の PR の CI が動かない（GitHub） | 標準の権限で作った PR では CI が動かない | PR を一度閉じて開き直す。`TAZUNA_BOT_TOKEN` を登録すると不要 |
| GitLab でドラフトを外しても CI がそのまま | GitLab は動き直さない | Run pipeline を押す（案内役が促す） |

## GitLab の案件

エージェントは GitLab の上では動かないので、全部手元の VS Code の Copilot で使う（相棒・点検役・実装）。MR は人が出し、相棒は説明の本文を書く。（案）の確かめはチャットで行い、記録のために MR のコメントにも `回答: n` を書く。issue に割り当てて任せる非同期の使い方はできない。

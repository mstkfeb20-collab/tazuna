# 振り分けの評価セット（ツアー予約）

ID 設計を、`docs/design/ID設計.xlsx` の書類の種類ごとに書いたもの（インプット）と、各行の正しい置き場所・振り分け先（正解）の組です。振り分けのスクリプトやスキル、置き場所の検査（Lint）を作ったら、ここで行ごとに採点します。

題材はツアー予約です。himotoki の評価用設計書（`samples/spec-extraction`）、tazuna の Java 見本（`src/`）と同じ業務ルールを使っています。

## 中身

| ファイル | 内容 | 振り分ける側に見せるか |
| --- | --- | --- |
| `design/S-xx-nnn_名前.md`（34ファイル） | 書類1つにつき1ファイル。502行 | 見せる |
| `design/ID設計.md` | 型と、評価セットの機能一覧・書類一覧 | 見せる |
| `expected.csv` | 正解。行ごとの正しい書類・設計項目・3属性・振り分け先・置き場所・持ち主 | **見せない** |
| `source.py` | インプットと正解の正本 | **見せない** |
| `build_eval.py` | `source.py` と型（`docs/design/ID設計.md`）から `design/` と `expected.csv` を作り、整合を検査する | — |
| `compat.py` | 評価用のスクリプトが型を読むための部品 | — |

### 書類の書き方

```markdown
# S-21-002 画面設計書：予約入力・確認・完了画面

## D-02002 画面項目定義

- [1] 予約確認画面には、入力内容・合計金額とその内訳…を表示する
- [2] 予約完了画面には、予約番号・振込期限・振込先口座を表示する
```

- 機能一覧と書類一覧（どの書類実体があり、機能別の書類がどの処理設計書のものか）は、`design/ID設計.md` に、案件の Excel の書き出しと同じ形で入れています。
- ファイルは書類実体ごとです。書類実体ID `S-21-002` は、書類ID `S-21`（画面設計書）の2つ目という意味で、番号に業務の意味はありません。
- 見出しは設計項目の項番と名前です。その書類の種類の記載項目にある項目だけを使えます。
- 行は `- [番号] 本文` で、番号は見出しの中で付けます。行IDは `書類実体ID/見出しの項番/番号`（例 `S-21-002/D-02002/2`）です。
- 番号は付けたら変えません。追加はその見出しの末尾の続きの番号で行い、振り直しはしません。使わなくなった行も消さずに「（廃止）」と書きます。順序が大事なときは、順序を決める見出しに「D-04001 の [1] → [3] の順」のように書きます。
- 別の見出しや書類に移すときは、元の行を廃止として残し、移った先で新しい番号を付けます。

## 正解の決め方

- **振り分け先**：正しい設計項目の3属性（性質・機械検査・業務承認）から、Excel の振り分け表の数式と同じルール（`compat.py` の `map_item()`）で決めます。
- **置き場所・持ち主**：振り分け先と、正しい書類の区分（共通設計・開発運用か、機能別設計か）から `place_owner()` で決めます。
- **属性の上書き（9行）**：行の中身が設計項目の既定と違うときだけ、その行の属性を上書きしています。例えば「会員番号：窓口担当が入力するときは必須」は、必須・任意の既定（値・形式、静的に可）と違い、条件付きなので振る舞い・実行で可です。`expected.csv` の「備考」列に違いを書いています。
- **書く場所の間違い（9行）**：評価のため、わざと違う見出しや書類に書いた行です。正解には正しい書類と設計項目を入れています。

| 判定 | 行数 | 例 |
| --- | --- | --- |
| 項目違い（同じ書類の別の見出しに書いた） | 7 | 「取消料は1円未満を切り捨てる」を計算式の下に書いた（正しくは端数処理） |
| 書類違い（別の書類に書いた） | 2 | 「大人人数と子供人数の合計は9人まで」を画面設計書の画面項目定義に書いた（正しくは処理設計書の相関チェック） |

## 採点の考え方（ツールを作るときの目安）

書く人が書類と設計項目を選ぶので、振り分け先そのものは項目から機械的に決まります。ツールの仕事は次の2つです。

- **置き場所の検査**：9行の間違いを見つけられるか。見つけた行に、正しい書類と設計項目を示せるか。正しい497行を間違いと言わないか。
- **属性の例外の検出**：9行の上書きを見つけられるか。上書きのない行で、余計な上書きを出さないか。

外れた行は「判定基準が足りない」「書き方が曖昧」「正解が間違い」のどれかに分けます。正解が間違いなら `source.py` を直します。

## 採点する

```bash
# 置き場所の形式（Lint、COMMON-007）。評価セットは形式の誤りがないので 0 件になる
python3 scripts/lint/common/design_docs.py _tazuna/id-design/eval/design
# 中身の判断（スキル base-design-check の指摘一覧を採点）
python3 _tazuna/id-design/eval/score.py 指摘一覧.tsv
```

スキルを試すときは、`design/`（`ID設計.md` を含む）とスキルだけを別の場所に写し、`expected.csv` と `source.py` が見えない状態で動かします。

## 作り直す

```bash
python3 _tazuna/id-design/eval/build_eval.py   # design/ と expected.csv
```

`build_eval.py` は、記載項目にない見出しや、インプットに現れない設計項目を見つけると、終了コード1で止まります。Excel の「例」がインプットのどの行とも一致しないときは、警告だけ出します（原本は Excel なので、例を書き換えても評価セットは作れます）。

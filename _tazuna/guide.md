# 新規プロジェクト向け ハーネス導入指南書

これから始めるプロジェクトで、AIコーディングエージェントが「正しく・保守しやすく」動く環境を初日から用意するための手引き。キックオフまでに型（tazuna）を取り込み、開発しながら育てる。

> このファイルは tazuna 本体の説明資料で、テンプレートには含まれません。案件のリポジトリでは `_tazuna/` ごと削除してください。

## 1. 基本の考え方

ハーネスは、エージェントに手順を教えるものではない。正しい方向へ探索し、自分で検証・修正できる環境である。人間は完了条件・不変条件・最終判断を握る。

### ルールは「破れない場所」から守る

エージェントに守らせたいことは、上の層で防げないかを先に考える。文章で伝えるのは最後の手段。

| 優先 | 層 | 防ぎ方 | 例 |
| --- | --- | --- | --- |
| 1 | 設計 | 間違えようのないAPI・型・ディレクトリ境界にする | 金額はMoney型しか受け取らない |
| 2 | Lint・型・テスト | 成果物の違反を機械的に検出する | floatでの金額計算、依存方向の逆転 |
| 3 | 実行して検証 | 実際に動かし、結果を証拠として残す | 画面キャプチャ、実行ログ |
| 4 | 文章 | skills・docsで判断基準を伝える | 業務上のトレードオフ |

これとは別に、エージェントの**行為**は hooks で止める。Lintが成果物を見るのに対し、hooksは作業中の操作を見る。

- **Lintにするもの**：コードに痕跡が残る違反。人が手で書いたコードにも効く。業務の不変条件は必ずこちら。
- **hooksにするもの**：取り返しがつかない操作（本番DB接続、`push --force`）、痕跡が残らない操作（テスト削除、`--no-verify`）、守るべきファイルの編集。
- 同じ判定を両方に書かない。hooksでコードの中身を確かめたいときはLintを呼ぶ。

### 新規プロジェクトだからできること

- **最初のコードを手本にする**：エージェントは既存コードを真似る。初期の数機能を丁寧に作れば、それが一番強い指示になる。
- **境界を先に決める**：レイヤーと依存方向を開発前にLintで固める。後から直すよりはるかに安い。
- **違反ゼロから始められる**：既存違反の一覧（ベースライン）は不要。Lintは初日から必須にする。

## 2. ディレクトリ構成

型リポジトリ（tazuna）から取り込む部分と、案件で作る部分を分ける。「型」と書いたものは標準化チームが管理し、git のタグで取り込む。

```
repo-root/
├─ AGENTS.md                     # 型の骨格＋案件のコマンド
├─ .github/
│  ├─ CODEOWNERS                 # パスごとの承認者
│  ├─ pull_request_template.md   # 証拠の欄（型）
│  ├─ skills/
│  │  ├─ base-*/SKILL.md         # 普遍の進め方（型）
│  │  └─ proj-*/SKILL.md         # ドメイン特有の進め方
│  ├─ hooks/                     # 行為のブロック（型＋案件追加）
│  └─ workflows/verify.yml       # CI（型）
├─ docs/
│  ├─ requirements/              # 要件・完了条件（ID付き）
│  ├─ domain/
│  │  ├─ invariants.md           # 業務の不変条件
│  │  ├─ glossary.md             # 業務用語集
│  │  └─ feature-map.md          # 機能一覧
│  ├─ architecture.md            # レイヤー・依存方向
│  └─ conventions.md             # 命名・作法
├─ scripts/lint/
│  ├─ run-all.sh
│  ├─ common/                    # 汎用チェック（型）
│  └─ domain/                    # 業務固有チェック
├─ src/test/                     # 要件IDに紐づくテスト
└─ harness/
   ├─ quality.md                 # 品質の考え方（工程ごとに何を見て・測り・判断するか）
   ├─ rule-log.md                # 違反の記録
   └─ metrics.md                 # 品質の記録・月次の指標
```

### 置き場所の判断基準

| 書きたいもの | 置き場所 |
| --- | --- |
| 常に守る原則・基本コマンド・参照先 | AGENTS.md（3〜5個、索引として短く） |
| 調査・設計・レビューの進め方 | `.github/skills/` |
| 業務ルール・仕様・用語 | `docs/domain/` |
| 完了条件 | `docs/requirements/` |
| 機械的に判定できる成果物のルール | `scripts/lint/` |
| 危険な操作の禁止 | `.github/hooks/` |

### skillsの命名

- `base-*`：どの案件でも使う進め方（例：`base-code-review`、`base-test-design`）。
- `proj-*`：ドメイン特有の進め方（例：`proj-reservation-review`）。
- proj は base と同じことをしない。base を前提にするときは本文で参照する。
- スキルに業務ルールを直接書かない。`docs/domain/` を参照させる。

### ルールの上書き

組織の標準 → 案件の標準 → タスク固有の順に優先する。業務の不変条件とセキュリティは上書き不可。命名・作法は理由を書けば上書き可。この上書きはdocsとLintに適用し、skillsには適用しない。

## 3. 役割分担

業務の正しさは社員、型は標準化チーム、中身は協力会社とエージェントが担う。承認者はCODEOWNERSで強制する。

| 場所 | 作る人 | 承認する人 | 使い方 |
| --- | --- | --- | --- |
| AGENTS.md | 標準化チーム（骨格）、案件リーダー（コマンド） | 案件リーダー | エージェントが常に読む。肥大化したらdocs・skillsへ移す |
| skills/base-* | 標準化チーム | 標準化チーム | 型として取り込む。案件では変更しない |
| skills/proj-* | 協力会社・社員 | 案件リーダー | baseと重ならないかレビューで確認する |
| hooks/・workflows/ | 標準化チーム | 標準化チーム | 案件ごとの禁止対象は案件リーダーが追加を提案 |
| docs/requirements/ | 社員 | 社員 | 要件IDを振る。テストの正本 |
| docs/domain/ | 社員 | 社員 | 不変条件・用語・機能一覧の正本。エージェントは設計前に読む |
| architecture・conventions | 案件リーダー | 案件リーダー | 技術スタックに合わせて書く |
| lint/common | 標準化チーム | 標準化チーム | 型として取り込む |
| lint/domain | 協力会社 | 社員 | docs/domainのルールを機械的にチェックできる形にする |
| テスト | テスト作成エージェント | 社員 | 実装を見ずに要件から作る。要件IDを必ず含める |
| harness/rule-log.md | レビューした人 | 案件リーダー | 違反を1行ずつ記録する |
| harness/metrics.md | 案件リーダー | ― | 月次で更新し、標準化チームに共有する |

案件リーダーはプロジェクトの技術責任者。社員か協力会社かはキックオフ前に決める。

## 4. 立ち上げ手順

ハーネスは最初から完成させない。最小構成で始め、各フェーズの成果物がそのままハーネスの中身になるように進める。

| フェーズ | やること | 成果物 | 担当 |
| --- | --- | --- | --- |
| 0. キックオフ前 | 型をタグ指定で取り込む。CODEOWNERSに担当者を入れる。CIとhooksを動かす | リポジトリの骨格 | 案件リーダー |
| 1. 要件定義 | 要件にIDを振り、完了条件を書く。不変条件・用語・機能一覧を作る | docs/requirements/、docs/domain/ | 社員 |
| 2. 基本設計 | レイヤーと依存方向を決め、Lintで固める。不変条件を型やAPIで防げないか検討する | architecture.md、lint/domain の初版 | 案件リーダー・協力会社 |
| 3. 開発初期 | 代表的な2〜3機能を人が丁寧に作り、手本にする。そこで得た作法をconventionsとproj-*に残す | 手本コード、conventions.md、proj-* | 協力会社・案件リーダー |
| 4. 本格開発 | エージェント中心に開発する。違反をrule-logに記録し、月次で改善する | rule-log.md、metrics.md | 全員 |

ポイントは2つ。

- **設計で防ぐ検討はフェーズ2でしか安くできない**。例えば金額をMoney型にする、状態遷移を専用API経由にする、といった判断は後から入れると高くつく。
- **フェーズ3の手本はエージェントに任せない**。最初のコードがその後のすべてのコードの手本になるため。

## 5. 日々の運用

エージェントは自分で検証してからPRを出し、人は証拠を見て判断する。

### 開発の流れ

1. チケットに要件IDと完了条件を書く（社員）。
2. エージェントが調査・設計・実装する。作業中はhooksが危険な操作を止め、編集のたびにLintが走る。
3. エージェントがテストと実行で検証し、OKになるまで自己修正する。
4. PRを出す。テンプレートの証拠欄（実行したコマンドと結果、画面キャプチャ）を埋める。
5. CIがLintとテストを再実行する。通らなければマージできない。
6. CODEOWNERSで割り当てられた人が、証拠と業務上の妥当性を見て承認する。

レビューでは、Lintで捕まえられる指摘をしない。人が見るのは、業務上正しいか、証拠が完了条件を満たしているかの2点に絞る。

### ミスが起きたとき

レビューで指摘した人が rule-log.md に1行記録し、「どの層で防ぐか」を次の順に検討する。

1. 設計を変えて、そのミスを起こせなくできないか
2. Lint・型・テストで機械的に検出できないか
3. 実行して検証すればエージェント自身が気づけないか
4. どれも無理なら、docsかskillsに文章で追記する

危険な操作（取り返しがつかないもの）はこの順番に関係なく、すぐにhooksで止める。

### Lintのエラーメッセージ

エージェントが自分で直せるように、何がダメか・なぜダメか・どう直すか・参照先を必ず書く。

```
ERROR [INV-001] src/main/java/com/example/domain/Bad.java:2
  内容: 金額を double / float で扱っています
  理由: 浮動小数点は丸め誤差で金額が1円ずれることがあります
  修正: com.example.domain.Money を使ってください（例: Money.yen(1000)）
  参照: docs/domain/invariants.md#INV-001
```

## 6. 改善と指標

月に1回、案件リーダーがrule-logを見返してハーネスを直し、結果をmetrics.mdに記録して標準化チームに共有する。

### 月次の見直しでやること

- 同じ違反が2回以上あれば、より上の層（設計・Lint）で防げないか検討する。
- 半年発火していないLintや、使われていないdocsは削除を検討する。
- 古くなったコードの書き方が残っていれば片付ける。先にLintで新しい発生を止めてから、既存の箇所を直す。
- AGENTS.mdが肥大化していれば、詳細をdocs・skillsへ移す。
- 他の案件でも使えそうな proj-* や lint/domain は、型への昇格候補として標準化チームに提案する。

### 記録する指標

| 指標 | 見るもの | 期待する動き |
| --- | --- | --- |
| rule-logの件数（防ぐ層ごと） | 仕組み化が進んでいるか | 「文章」の割合が下がる |
| 追加したLintルール数 | ミスがルールに変わっているか | 初期に増え、やがて落ち着く |
| PR数とリバート率 | エージェントの成果を信頼できるか | PR数が増えてもリバート率が上がらない |
| 同じレビュー指摘の再発数 | 改善が効いているか | 減る |

指標は案件の優劣を付けるためではなく、組織としてハーネスが効いているかを説明するために使う。

## 8. キックオフ前のチェックリスト

すべてにチェックが入ってから、エージェントに開発を任せ始める。

### 体制

- [ ] 案件リーダーを社員が担うか、協力会社が担うかを決めた
- [ ] CODEOWNERSに、業務（社員）と型（標準化チーム）の承認者を入れた
- [ ] 月次の見直しの日程と参加者を決めた

### リポジトリ

- [ ] 型をタグ指定で取り込んだ（「Use this template」か、テンプレートからの複製かを決めた）
- [ ] `_tazuna/` を削除した
- [ ] CIでLintとテストが必須になっている
- [ ] hooksが動き、本番接続やテスト削除が止まることを確認した
- [ ] PRテンプレートに証拠の欄がある

### 中身

- [ ] AGENTS.mdに案件のコマンドと参照先を書いた
- [ ] 不変条件・業務用語・機能一覧の初版がある
- [ ] 要件にIDが振られ、完了条件が書かれている
- [ ] レイヤーと依存方向をLintで固めた
- [ ] 手本となる機能を人が作り、その作法をconventionsに残した

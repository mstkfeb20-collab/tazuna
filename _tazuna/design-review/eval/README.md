# 設計書レビュー（base-design-review）の評価セット

tazuna 本体専用（案件では `_tazuna/` ごと削除する）。わざと欠陥を入れた小さな設計書一式で、スキル `.github/skills/base-design-review/` がどれだけ欠陥を拾い、どれだけ誤って指摘するかを測る。

- `design/`・`docs/domain/glossary.md`・`db/schema/`: レビューする設計書一式（予約取消と振込データ取込の書類 11 件・行 69 行）
- `expected.csv`: 欠陥の答え（種別・根拠の行ID）。F18〜F20 は初回の実行で見つかった、答えに入れ忘れていた欠陥。F21〜F22 は「書かれていない」型の欠陥（年2桁の解釈、存在しないファイルの参照）で、パイロットの実装前の版を Copilot でレビューしたときに見落とした型に合わせて2回目から足した
- `stars.csv`: ★（共通の必須の見出しが空なのに機能の書類が先に決めている）ごとの、扱いの答え（1 共通に書く・2 機能に任せる・3 置き場所の誤り）。3回目から。2回目までの F23（★）はこちらに移した
- `decoys.csv`: 問題のない行（それらしいが指摘にしない例：共通の方針に沿った機能ごとの決定、用語集にある言い換えなど）
- `score.py`: 採点。指摘の根拠の行IDが欠陥の行IDと重なれば当たり、種別も合えば種別一致

## 試し方（答えを見せない）

`design/` などの入力とスキル、`scripts/design/catalog.py`・`review_pack.py` だけを別のフォルダに写し、答え（expected.csv・decoys.csv）を見られないエージェントにスキルどおりにレビューさせる。結果の TSV を `score.py` で採点する。スキルの例に、この評価セットの欠陥を書かない（書くと測れなくなる）。

3回目は、★ を1件ずつ指摘にせず「1 共通に書く・2 機能に任せる・3 置き場所の誤り」の判断を出すようにスキルを直した後（パイロットの実装前の版で、Copilot が ★ を丸写しして指摘が埋もれたため）。

2回目は、材料に「機械で分かっている書かれていないこと」（★・ファイルがない参照・必須の見出しが空）と空の定義を足し、スキルに「書式の解釈」の観点を足した後。

注意: 欠陥は人が入れたもので、本物の設計書の欠陥よりも見つけやすい。1回の実行で、モデルは Claude（tazuna の作業と同じもの）。Copilot で使う別のモデルでは試していない。
